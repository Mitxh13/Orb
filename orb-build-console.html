ORB

Virtual digital wallet · 21-day build console

Orb is a full-stack digital wallet that simulates UPI/Paytm-style payments using a fictional currency called ORB. Every account opens with a seeded balance of ₹1,00,000 — no bank, no card, no real money ever touches this system. This console is where you track the build: what ships each day, how the pieces connect, and how far along you are.

What it does

  • Registers a user and auto-creates a wallet with ₹1,00,000, inside the same transaction as signup.
  • Sends money peer-to-peer between wallets, atomically — a debit and a credit that either both happen or neither does.
  • Generates a scannable QR code for a wallet, and reads one back via the camera to prefill a payment.
  • Lists paginated transaction history, filterable by type and date, split into sent vs. received.
  • Emails the receiver on every incoming transfer, without blocking the API response.

Design goals

  • Production-grade architecture — not a tutorial app.
  • Atomic double-entry bookkeeping for every transfer.
  • Mobile-first responsive UI — works on a phone browser and a laptop equally well.
  • Stateless JWT authentication with an access + refresh token flow.
  • Security-first: BCrypt everywhere, a separate transfer PIN, account lockouts, rate limiting.

Architecture

Three tiers, one direction of truth: browser → API → database.

System layout

Browser — React SPA
Served from Vercel's CDN
HTTPS · REST/JSON
JWT Bearer token
Spring Boot API — Railway :8080
Stateless, no server-side sessions
Spring Security — JWT filter chain Service layer — @Transactional boundaries JPA / Hibernate — ORM
JDBC
PostgreSQL 15
Railway-managed database

The frontend is a single-page app with no server rendering. It talks to the API purely over HTTPS — there's no server-side session or cookie anywhere. Every request carries its own signed JWT, so any API instance can serve any request.

Authentication flow

1
User registers
POST /api/auth/register
2
Server creates User + Wallet
Same @Transactional — never one without the other
3
Server returns tokens
{ accessToken, refreshToken, user }
4
Frontend stores and attaches
Authorization: Bearer <accessToken> on every request
5
Filter validates on every protected route
JwtAuthFilter, once per request
6
On 401, refresh
Frontend calls POST /api/auth/refresh
7
Silent retry
New accessToken retries the original request

Access tokens expire after 24 hours, refresh tokens after 7 days. The JWT secret needs to be at least 32 characters and live in an environment variable — never hardcoded in source.

P2P transfer flow — the critical path

1
Validate JWT
Identify the sender
2
Validate the transfer PIN
BCrypt.matches against transfer_pin_hash
3
Look up the receiver
By wallet_tag
4
Guard: sender ≠ receiver
Self-transfer is rejected
5
Guard: balance ≥ amount
Checked before the transaction opens
6
@Transactional block
Debit sender, credit receiver, insert transaction row — commit or full rollback
7
@Async email to receiver
Doesn't block the response
8
Return
{ success, referenceId, newBalance }
Critical
@Transactional is non-negotiable on the transfer method. Without it, a crash between the debit and the credit leaves money in a partial state. Both sides succeed together, or both roll back.

Flyway migration rules

Always create new migration files in order. Never edit a file that has already run — Flyway tracks checksums and fails on startup if a past file changes.

db/migration/ ├── V1__create_users_table.sql ├── V2__create_wallets_table.sql ├── V3__create_transactions_table.sql └── V4__create_notifications_table.sql To add a column later, create a new file: └── V5__add_phone_to_users.sql
Critical
Never modify V1–V4 after they've run once. Need a schema change? Create V5, V6, and so on.

Talking points

What to say when someone asks about a design decision.

@Transactional on transfers?
The debit and credit either both succeed or both roll back. No partial state is possible, even on a crash mid-operation.
Wallet creation atomicity?
The user row and wallet row are created in the same transaction — a user can't exist without a wallet.
Why DECIMAL, not float?
DECIMAL(15,2) in Postgres and BigDecimal in Java. Floating-point math drifts, and that drift becomes real currency errors.
Why stateless JWT?
Zero session state on the server. Any instance can serve any request — no sticky sessions needed to scale horizontally.
Why @Async for email?
Notification emails run on a separate thread pool, so they never add latency to the response the user is waiting on.
Flyway over ddl-auto?
Schema changes are version-controlled SQL files. In production, Hibernate shouldn't be guessing at the schema.
Mobile-first Tailwind?
Base styles target mobile, then sm: and md: breakpoints add the larger-screen layout. The sidebar collapses to a bottom nav on small viewports.
Transfer PIN security?
Stored as a separate BCrypt hash from the login password, required on every transfer — a compromised JWT alone can't move money.

Deploy

Local setup, environment variables, and shipping to Railway + Vercel.

Local setup

1
Clone and create the database
git clone https://github.com/Mitxh13/Orb.git cd Orb -- in psql or pgAdmin CREATE DATABASE orb_db;
2
Configure application.yml
spring: datasource: url: jdbc:postgresql://localhost:5432/orb_db username: YOUR_POSTGRES_USER password: YOUR_POSTGRES_PASSWORD jwt: secret: YOUR_32_CHAR_MINIMUM_SECRET expiration: 86400000 # 24 hours refresh-expiration: 604800000 # 7 days mail: host: smtp.gmail.com port: 587 username: your@gmail.com password: your-gmail-app-password
3
Start the backend
./mvnw spring-boot:run # API: http://localhost:8080 # Swagger: http://localhost:8080/swagger-ui.html
4
Start the frontend
cd frontend npm install # frontend/.env VITE_API_BASE_URL=http://localhost:8080 npm run dev # http://localhost:5173
5
Run tests
./mvnw test # uses H2 in-memory — no local Postgres needed for tests
